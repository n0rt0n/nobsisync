# NObsiSync

Плагин Obsidian для двусторонней синхронизации хранилища через Яндекс.Диск.
Работает на десктопе и на мобильных (iOS/Android).

## Что делает

- Двусторонняя синхронизация заметок и вложений с папкой на Яндекс.Диске
- Определение изменений по md5 — Диск отдаёт хеши прямо в листинге, так что
  ложных срабатываний от «поехавшего» mtime не бывает
- Три состояния вместо двух: локальное, удалённое и снимок последней
  синхронизации. Без снимка нельзя отличить «файл создан здесь» от «файл удалён
  там», и плагин начал бы воскрешать удалённые заметки
- Конфликты не теряются: по умолчанию сохраняются обе версии
- Запуск вручную, по интервалу и опционально при старте

Папка `.obsidian` не синхронизируется — настройки, темы и плагины остаются
локальными для каждого устройства.

## Получение OAuth-токена

Токен выдаётся один раз и живёт год.

1. Откройте <https://oauth.yandex.ru/client/new/> и создайте приложение
2. Платформа — «Веб-сервисы», Redirect URI — `https://oauth.yandex.ru/verification_code`
3. Доступы — «Яндекс.Диск REST API»: `cloud_api:disk.read` и `cloud_api:disk.write`
4. После создания скопируйте `ClientID` и откройте в браузере:

   ```
   https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENT_ID
   ```

5. Подтвердите доступ — токен появится в адресной строке после `access_token=`
6. Вставьте его в настройки плагина и нажмите «Проверить подключение»

Токен хранится в `data.json` плагина в открытом виде — как и у любого плагина
Obsidian. Учитывайте это, если раздаёте устройство или бэкапите `.obsidian`
публично.

## Установка

### Через BRAT (рекомендуется, работает и на мобильных)

[BRAT](https://github.com/TfTHacker/obsidian42-brat) ставит плагины из
GitHub-релизов и умеет их обновлять.

1. Установите BRAT из каталога плагинов Obsidian
2. Команда «BRAT: Add a beta plugin for testing» → введите `владелец/nobsisync`
3. Включите NObsiSync в списке плагинов

Репозиторий должен быть публичным: авторизоваться к приватным BRAT не умеет.

### Вручную

Скопируйте `main.js`, `manifest.json` и `styles.css` в
`<хранилище>/.obsidian/plugins/nobsisync/` и включите плагин в настройках.
На Android папка `.obsidian` скрытая — нужен файловый менеджер с показом
скрытых файлов.

### Выпуск новой версии

```bash
npm version patch     # поднимет версию в package.json, manifest.json и versions.json
git push && git push --tags
```

По пушу тега GitHub Actions прогонит типы и тесты, соберёт `main.js` и создаст
релиз с тремя файлами. Если тег не совпадает с версией в `manifest.json`,
сборка падает — расходящиеся версии ломают обновление через BRAT.

### Разработка

```bash
npm install
npm run dev      # esbuild в режиме watch
npm run deploy   # скопировать сборку в хранилище
```

`deploy` сам находит хранилище в конфиге Obsidian — то, что открыто сейчас, иначе
последнее открывавшееся. Можно указать и явно:

```bash
npm run deploy -- "/путь/к/хранилищу"
OBSIDIAN_VAULT="/путь/к/хранилищу" npm run deploy
```

После копирования — «Reload app without saving» в палитре команд Obsidian.

Симлинк вместо копирования тоже работает и избавляет от шага `deploy`, но тогда
`data.json` плагина — вместе с OAuth-токеном в открытом виде — окажется в папке
репозитория, а не в хранилище. На мобильных симлинки недоступны в любом случае:
там три файла сборки нужно класть в
`<хранилище>/.obsidian/plugins/nobsisync/` вручную.

```bash
npm run typecheck   # tsc без эмита
npm test            # тесты
npm run build       # проверка типов, тесты и продакшн-сборка в main.js
```

Тесты гоняют движок синхронизации на заглушках файловой системы и Диска, без
запуска Obsidian. Файловая система в заглушке сравнивает имена побайтово — как
NTFS и ext4, — поэтому ошибки в работе с нормализацией всплывают сразу, а не
только на Windows у пользователя.

## Как разрешаются конфликты

Конфликт — это когда файл изменился и локально, и на Диске, причём по-разному.
Варианты в настройках:

| Режим | Поведение |
|---|---|
| Сохранять обе версии (по умолчанию) | Локальная версия переименовывается в `Заметка (конфликт устройство 2026-07-28 16-42).md`, каноническим именем становится версия с Диска, переименованная копия уезжает на Диск |
| Локальная побеждает | Локальная версия затирает удалённую |
| Версия с Диска побеждает | Удалённая версия затирает локальную |
| Побеждает более свежая | Сравнение по времени изменения |

Режим по умолчанию сходится: после синхронизации оба устройства видят обе
версии под одинаковыми именами. Переименование делается через `adapter.rename`,
а не `vault.rename`, — ссылки в других заметках остаются указывать на
каноническое имя, а не переезжают на конфликтную копию.

Если файл удалён с одной стороны и изменён с другой, побеждает правка: файл
воскресает. Потерять правку хуже, чем не заметить удаление.

## Где смотреть, что произошло

- **Статус-бар** — время последней синхронизации (на десктопе)
- **Настройки → NObsiSync → Журнал** — последние пять прогонов с цветной меткой
  состояния и кнопкой «Открыть журнал»
- **Палитра команд → «Показать журнал синхронизаций»** — вся история: по щелчку
  запись разворачивается в список перенесённых файлов и ошибок. Есть кнопка
  копирования в буфер
- **`sync.log`** в папке плагина — тот же журнал текстом. Нужен там, где UI
  недоступен: посмотреть с телефона, грепнуть, приложить к отчёту об ошибке

История хранит последние 50 прогонов. Лог-файл обрезается с головы при
превышении 256 КБ. Ошибка записи лога никогда не роняет синхронизацию.

Уведомление после прогона показывает итог, но автоматическая синхронизация
молчит, когда изменений не было, — иначе она дёргала бы уведомлением каждые
несколько минут. Поэтому единственный надёжный способ узнать, что происходило
ночью, — журнал.

## Расход запросов к API

Яндекс не публикует точные лимиты REST API Диска — он просто отвечает `429` с
заголовком `Retry-After`, когда вы упёрлись. Клиент такие ответы повторяет с
экспоненциальной задержкой, а `4xx` не повторяет: смысла нет, а лимит тратится.

Сколько стоит прогон:

| Операция | Запросов |
|---|---|
| Листинг папки | 1 на каждые 200 объектов |
| Выгрузка файла | 2 (ссылка + передача) |
| Скачивание файла | 2 (ссылка + передача) |
| Удаление файла | 1 |
| Создание папки | 1, один раз за прогон |

Синхронизация без изменений стоит столько запросов, сколько папок в хранилище.
Для хранилища с одной вложенной папкой это 2 запроса; при интервале в 15 минут —
меньше 200 запросов в сутки.

Папки, увиденные в листинге, запоминаются на время прогона. Без этого кэша
`ensureDirChain` дёргал бы `PUT` на каждый сегмент пути при каждой выгрузке,
получая `409` и сжигая запросы тем быстрее, чем глубже вложенность.

Фактический расход за прогон виден в журнале.

## Файлы, изменённые вне Obsidian

Плагин не подписан на события хранилища — на каждом прогоне он сам обходит
файловую систему. Поэтому правки из любой программы (KeePass, git, файловый
менеджер, скрипт) видны наравне с правками в самом Obsidian.

Синхронизируются и файлы с расширениями, которых Obsidian не знает: он не
показывает их в списке файлов, но на диске они лежат и в обход попадают.

Изменение замечается, если разошлись содержимое и при этом размер или время
изменения файла. Единственная слепая зона — программа, которая переписывает
файл, сохраняя и прежний размер, и прежний mtime; такие встречаются редко.
Сбросить кэш и пересчитать всё заново можно кнопкой «Сбросить снимок».

### Базы паролей и подобное

Работает, но `*.lock` стоит добавить в исключения. KeePass держит рядом с базой
файл блокировки, пока она открыта; уехав на другое устройство, он заставит
KeePass считать базу занятой.

Правка базы одновременно на двух устройствах даст конфликтную копию, а не
испорченный файл, — но сливать её придётся средствами самого KeePass.

## Переименования

Отдельного отслеживания переименований нет: для плагина это удаление старого
имени и создание нового. Итог тем не менее правильный и без дубликатов.

Устройство A переименовало `note.md` в `idea.md`. При синхронизации A выгружает
`idea.md` и удаляет `note.md` с Диска. Устройство B скачивает `idea.md`, а свой
`note.md` отправляет в `.trash`. Оба остаются с одной заметкой под новым именем.

Исключение — когда устройство B успело изменить `note.md` и ещё не
синхронизировалось. Тогда работает правило «правка побеждает удаление», и на
обоих устройствах окажутся оба файла: `idea.md` с прежним содержимым и
`note.md` с правкой. Это выглядит как дубликат, но файлы разные, и потерять
правку было бы хуже.

## Нормализация имён

Ключ, по которому сопоставляются стороны, всегда приводится к NFC. Обращение же
к файлу идёт тем именем, под которым он реально существует, — эти две вещи
разделены намеренно:

| Платформа | Поведение файловой системы |
|---|---|
| macOS (APFS, HFS+) | Имя хранится как дано, но поиск идёт без учёта нормализации: NFD-файл открывается по NFC-имени |
| Windows (NTFS) | Сравнение побайтовое, нормализации нет: NFD-файл по NFC-имени не откроется |
| Linux (ext4, btrfs) | Сравнение побайтовое, Unicode не интерпретируется вовсе |
| Android, iOS | Работа идёт через слой Obsidian поверх NFC-имён |

Если бы плагин обращался к файлам по нормализованному ключу, на Windows и Linux
заметка с NFD-именем (принесённая с Mac через флешку или git) не читалась бы, а
её удаление молча не срабатывало бы — и на следующем проходе она возвращалась бы
из небытия. Новые файлы создаются в NFC, так что со временем имена приходят к
единой форме.

## Безопасность данных

- Удаления на Диске идут в корзину Диска (`permanently=false`) — восстановимо
- Локальные удаления по умолчанию идут в `.trash` хранилища
- Снимок можно сбросить: плагин просто забывает историю и сравнивает стороны
  заново, объединяя содержимое. Файлы при этом не удаляются

## Ограничения

- Файлы переносятся целиком в памяти, поэтому по умолчанию действует лимит в
  100 МБ на файл (настраивается). Докачки и дозагрузки нет
- Синхронизация не инкрементальная по содержимому: изменённый файл передаётся
  целиком
- Переименование не распознаётся как переименование: файл передаётся заново
  целиком, а не переставляется на Диске. Результат корректный (см. ниже), но для
  крупного вложения это лишний трафик
- Если два файла в одной папке различаются только формой нормализации имени,
  плагин посчитает их одним и засинхронизирует только один из них

## Структура

```
src/
  main.ts       класс плагина, команды, статус-бар, вкладка настроек
  sync.ts       сканирование, трёхстороннее сравнение, исполнение плана
  yandex.ts     клиент REST API Яндекс.Диска поверх requestUrl
  md5.ts        MD5 на чистом JS (node:crypto на мобильных недоступен)
  settings.ts   типы настроек и значения по умолчанию
  util.ts       пути, глобы, пул задач
```
